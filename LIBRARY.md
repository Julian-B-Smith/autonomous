[L0001] A `sed` on `/etc/ssh/sshd_config` is not hardening on a cloud image — drop-ins are Included FIRST and OpenSSH is first-value-wins | canonical | added: 2026-08-14 | tags: cloud-image | lesson: Ubuntu's stock `sshd_config` `Include`s `sshd_config.d/*.conf` near the TOP, and OpenSSH takes the FIRST value it meets for each keyword. So a hardening script that `sed`s `PasswordAuthentication no` into the main file is silently overridden by cloud-init's `50-cloud-init.conf` (`PasswordAuthentication yes`), and the file LOOKS hardened while the effective config is not. Write your own `00-<project>-hardening.conf` (sorts first, so it wins over anything cloud-init writes later) and ASSERT the effective config with `sshd -T`, never by reading the file — prove the result, not the artifact. Generalizes to every cloud-image box the fleet deploys. | evidence: life-os-app VPS, verified live 2026-08-14 in response to autonomous-lifeos-001: `bootstrap.sh`'s sed had run, `sshd -T` showed `passwordauthentication yes`; tens of thousands of failed-password attempts in 30d had been hitting an endpoint the script believed was closed (bounded by a locked deploy-account password + `PermitRootLogin no`, so no breach — a defense-in-depth gap). Fixed with the 00- drop-in + `sshd -T` assertion in `bootstrap.sh`; password auth verified refused from outside. Filed by the Life-OS resident via autonomous-lifeos-001 response-1; Promoted from life-os-app#L0002 (their copy: tier candidate, tags deploy-ops/security). | falsifier: on a stock Ubuntu cloud image with a conflicting `50-cloud-init.conf`, `sshd -T` shows the sed'd main-file value taking effect. | origin: life-os-app#L0002

[L0002] A gate that has never fired against known-bad input is not known to be a gate — and `git grep -E` is POSIX ERE, so `\s`, `\d`, `\b` all silently match nothing | canonical | added: 2026-08-14 | tags: gate-blindness, detector-calibration | lesson: `git grep -E` does not support Perl-class escapes. The only defense that catches this class is procedural: before trusting any new detector, plant a KNOWN-BAD line and watch it fire, plant a KNOWN-GOOD near-miss and watch it stay quiet, then run the clean tree. Comment the trap at the pattern site — the next agent will "simplify" it back. | evidence: leak_scan.py 2026-07-13 (dead absolute-path detection, caught only by testing against a known-bad); life-os-app `verify` ip_gate 2026-08-14 (planted the real leaked IP, 0 hits, root cause `\b`). [L0005] A detector shares assumptions with the thing it measures, so its first run against a foreign corpus is the only cheap test of those assumptions — and a must-read-zero check needs a paired corruption or it cannot fail | canonical | added: 2026-08-18 | tags: detector-calibration, gate-blindness | lesson: Two halves, both learned the same day. (b) The obvious control — "our own corpus must read zero" — CANNOT FAIL: if the file-level path becomes a no-op it returns zero and passes. Measured: the suite passed 12/12 against a deliberately neutered `validate_file`, because every other test exercised the entry-level path. A must-read-zero assertion is only meaningful PAIRED with a corruption of the same file that must read non-zero. | evidence: kit/gates/library_validate.py, 2026-08-18 — three false positives on HYPERSAW's LIBRARY and autonomous's own on first run; the inertness hole demonstrated by monkeypatching `validate_file` to return [] and observing 12/12 green; paired control added and re-proven to fail against the same neutered function. [L0006] A probe that runs the target's own oracle inherits the oracle's side effects — "left untouched" must be true of every file the oracle writes, not only the files the probe wrote | canonical | added: 2026-08-18 | tags: probe-side-effects, effective-state | lesson: `currency.py`'s gate-fires probe plants a known-bad file and runs the target's `./verify fast`. A correctly firing gate exits 1 — and the target's `record()` writes that exit into `.harness/last-verify.json` and deletes `.harness/dirty`. The probe removed its plant and called the repo untouched; the repo's Stop hook then blocked on a red that was actually the probe PASSING, with a clean tree, seconds after the resident's own green close — a symptom designed to look like a defect. The fix is symmetric with the plant: snapshot every file the oracle writes before, restore byte-for-byte after (including "absent"), in the same try/finally. General form: whenever a check invokes a subprocess that has its own record-keeping, the check's cleanup contract extends to that record-keeping. | evidence: juce-rag, 2026-08-18 — record read `exit:1 / 04:16:00Z` seconds after a green close, re-run green at 04:16:17; found by the first live Step 6 verification (retrofit_verify → currency → their verify). Fixed in kit 2.2.2 with `_harness_snapshot`/`_harness_restore`; the new test fails against the prior code with the exact `exit:1` overwrite juce-rag saw. | falsifier: a probe that runs a target's oracle and, on a target whose oracle has side effects, leaves every such file byte-identical (or identically absent) after a firing run.
[L0007] A gate that fires is worthless if the operator reads the exit code and proceeds anyway — chain the commit TO the oracle, never merely after it | canonical | added: 2026-08-18 | tags: operator-error, oracle-discipline | lesson: The leak_gate caught an absolute home path in a visitor's filed notice, exactly as designed, and printed `verify: 1`. The commit ran anyway and was pushed to a PUBLIC repo — because the shell line was `./verify fast; echo $?; git commit && git push`, where the exit code was DISPLAYED rather than DEPENDED ON. Every ingredient of the safeguard worked; the operator supplied the bypass. Two corrections, both structural rather than resolutions to be careful: (a) the commit must be chained to the oracle with `&&`, so a red exit cannot reach `git` at all; (b) content arriving from OUTSIDE the repo — a visitor's brief, a filed notice, any pasted tool output — is gate-checked BEFORE it is staged, because that is the class of content whose author never ran our gates. Related: the source defect was that `currency.py` rendered an absolute path and Step 6 told every repo to paste that render into a public repo, so the leak was manufactured by the kit and then waved through by the operator. | evidence: autonomous, 2026-08-18 — commit dd0f98e pushed `integrations/foundations/retrofit-2.2.1.md:13` carrying a machine home path after `./verify fast` returned 1 and the value was echoed to the terminal; tip rewritten, source fixed in kit 2.2.3 (`_tilde`). | falsifier: a session where the oracle exits nonzero and no commit exists that postdates it, with the shell history showing the commit was chained by `&&` rather than sequenced by `;`.
[L0008] In a repo that receives asynchronous writes from other sessions, a green oracle chained by `&&` still does not cover `git add -A` — the tree can change between the check and the stage | canonical | added: 2026-08-18 | tags: mailbox-race, oracle-discipline | lesson: The commit that first pushed a machine path into this public repo was correctly chained: `./verify fast && git add -A && git commit`. The gate was green when it ran. A visitor session filed a retrofit notice into `integrations/` in the seconds between the check and the stage, and `-A` swept it in. The sibling lesson L0007 (chain the commit TO the oracle) is necessary and NOT sufficient here: chaining closes the operator's bypass, not the race. What closes the race is staging explicit paths instead of `-A`, or re-running the gate against the staged set — and noticing that `-A` in a mailbox repo also performs a resident act the charter reserves, committing a visitor's uncommitted brief. General form: `add -A` assumes the working tree is yours alone; in any repo that is a drop point for other agents, that assumption is false by design. | evidence: autonomous, 2026-08-18 — 78f0f5a carried `integrations/foundations/retrofit-2.2.1.md` with an absolute home path; the same session's verify had returned green moments before, and the file was not present at check time. [L0009] A tool that writes into a foreign working tree owes that tree cleanup its own `finally` cannot guarantee — sweep on entry, because the interrupted run is the one that leaves the mess | canonical | added: 2026-08-18 | tags: probe-side-effects, foreign-tree | lesson: `currency.py`'s gate probe plants an identity path in the target repo and removes it in a `finally`. A `finally` does not run when the process is killed, and a timeout killed one: the plant survived, untracked and unignored, one `git add -A` away from committing identity paths that `leak_gate` ignores BY DESIGN — the exclusion added in 2.3.0 to stop probes reddening concurrent runs is exactly what would have made the committed leak invisible afterwards. Cleanup on exit is best-effort by construction; cleanup on ENTRY is not, because the next run is alive by definition. General form: any tool writing into a tree it does not own should remove its own orphaned artifacts before creating new ones, deciding staleness by AGE rather than pid (pids are reused, and a live sibling's artifact must survive). Corollary learned the same hour: the sweep only works if every probe uses the SAME name the exclusion knows — a differently named plant (`chk-win.md`) reintroduced the 2.3.0 race in a repo whose gate was correct. | evidence: autonomous, 2026-08-18 — reported by Place, whose project-local `plant_not_tracked` check caught a real orphan from a timed-out run, and by attest, whose `./verify` exited 1 on a foreign `chk-win.md` that vanished a command later. Fixed with `_sweep_stale_plants(repo, max_age=600)` called before planting in both `currency.py` and `kit_audit.py`, and by routing every probe through one named helper. | falsifier: a probe tool that, after being SIGKILLed mid-run against a foreign repo, leaves that repo with no artifact of its own on the next invocation — without any guard living in the target repo.
[L0010] An artifact two independent readers misread is defective, however defensible its behaviour | canonical | added: 2026-08-18 | tags: interface-honesty, versioning | lesson: `.kit/MANIFEST` recorded `kit_version: 2.4.0` while the kit was at 2.4.1, because a TOOL-ONLY bump changes no vendored bytes, so nothing was rewritten and the version line rotted. [L0011] A pinned dependency in a TEMPLATE ages on someone else's schedule, so "we have not changed it" is not a reason to believe it still works | canonical | added: 2026-08-18 | tags: template-lag, external-clock | lesson: `kit/templates/ci.github.yml` pinned `actions/checkout@v4` and `actions/setup-python@v5`. [L0012] A gate with an optional-dependency FALLBACK needs CI on the branch without the dependency, or the fallback rots unseen | canonical | added: 2026-08-18 | tags: gate-blindness, fallback-rot | lesson: vertex's Layer-0 checker parses YAML with PyYAML when present and a hand-rolled parser when not. CI always had PyYAML, so the fallback branch had never run under test — and carried two defects: a quote-blind check that rejected every valid map, and `source: ""` satisfying a `\S+` test, which silently un-enforced the cardinal non-empty-source rule. The general form is 2.2.0's presence-is-not-behaviour one level down: it is not enough that the fallback EXISTS and the gate passes, because the path CI exercises is not the path a user without the dependency runs. The pairing vertex arrived at is the useful shape, and the second half is the part usually skipped: run the fallback in CI, AND make the log SAY that is what ran. They had been inferring "no PyYAML here" from the interpreter path, which is the presence-not-behaviour trap one level up — the inference stops being true the day the runner image ships the dependency, silently. [L0013] A repo's format-on-write hook will silently rewrite VENDORED bytes and break their checksum, and the failure surfaces later as a mystery, not at the point of cause | canonical | added: 2026-08-18 | tags: vendoring, hook-interference | lesson: Kit mechanism is vendored into `.kit/` and pinned by sha256, so `kit_integrity` reds on any local edit — which is the point. A PostToolUse prettier hook rewriting a written file is a local edit that nobody intended and nobody sees: the bytes change, the hash stops matching, and `./verify` goes red at some later run with no connection to the formatter that did it. Every repo with a format-on-write hook has this exposure, and `kit_sync` does not warn at sync time, which is the moment the exposure is created. [L0014] Four checks each asked a question next to the one that mattered, and the gap was always the same shape: the artifact exists, and cannot take effect | canonical | added: 2026-08-18 | tags: gate-blindness, effective-state | lesson: In two days the same defect surfaced four times, each time in a check written by someone who had already learned the lesson from the previous one. `contains:leak_gate` asked whether the gate's NAME appeared (2.2.0); the vendoring check asked whether the files were PRESENT while nothing sourced them (2.4.0); the `.gitattributes` check asked whether the file was on DISK while it was untracked (2.5.0); and `kit_sync --check` reported `current` for canonical bytes that were untracked, so a clone and CI got nothing while the repo read healthy (terrane). Ask what consumes this, then ask whether it can. **The correct fix is not one broad check**: `kit_sync --check` deliberately still answers only about the vendored FILES, because a verdict that means three things means nothing — it simply had to stop saying `current` about something healthy on exactly one machine. | evidence: autonomous, 2026-08-18 — 2.2.0 (spectral-morph), 2.4.0 (Decision 65, ten drifted gates), 2.5.0 (Tonality, untracked .gitattributes), and the intersection found by terrane, whose repo had .kit/ checksum-current, untracked and unsourced, with no ./verify at all. 23 fleet repos read `untracked` the moment the status existed — most of them because this session synced .kit/ into them and correctly did not commit in someone else's repo. | falsifier: a check reporting an artifact healthy where its actual consumer cannot reach it — or a repo passing every kit check while a fresh clone of it has no gates.
